# 让变动自己进频道，也让 Agent 的上下文更看得见

最近把 Joi 里两块很有手感的能力整理顺了，一个是定时任务，一个是 context 显示。它们看上去分属两端，一边负责把外部变化稳定送进频道，一边负责把 Agent 每一轮到底吃了多少上下文摊开来看，放在一起之后，整个协作链路会清楚很多。

定时任务这次最实用的地方，在于它没有把外部事件原样倒进聊天窗口。调度层会先抽取事件、限制单次数量、按模板压成短消息，内容长了就只保留摘要，把完整 payload 挂成 `scheduler-event.json`。如果一批结果本质上还是同一组内容，系统会再算一层内容哈希，和上一次发送结果对比，内容没变就不再重复发消息。这样频道里留下的是“有变化的结论”，信息密度会高很多，噪音也能压下去。

这条链路还有一个很接地气的用法：直接接本地命令源。像 `a1 events` 这类代码平台事件流，现在就可以通过 scheduler 的 command source 接进 Joi。本地拉到 MR、评审、流水线、仓库动态之后，先做一轮压缩，再写成频道消息；需要时还可以在消息里带上 `@agent`，继续把后续处理交给对应 Agent。对日常协作来说，这相当于把代码平台的变动提醒搬进了本地工作台，接收会更顺，跟进也更自然。

另一块是 context 显示。现在 Agent 消息上方会直接给出这一轮 prompt 的大致体积，hover 到头像还能看到 `Bootstrap`、`Identity`、`Memory`、`Thread/Channel`、`Latest Message` 各自占了多少。Claude 这类模型一旦上下文偏大，等待时间会立刻有体感，有了这组数字，排查时心里会更有底。

```mermaid
flowchart LR
    A[a1 events / HTTP / shell / command] --> B[Scheduler 抓取事件]
    B --> C[字段裁剪与模板渲染]
    C --> D[摘要压缩<br/>完整数据挂附件]
    D --> E[内容 Hash 去重]
    E --> F[频道消息]
    F --> G[@agent 继续处理]
    F --> H[消息顶部显示 Prompt ctx]
    H --> I[头像 Hover 查看分项占比]
```

这两块能力放到一起看，其实都在做一件事：让信息流更主动，也让 Agent 的工作过程更透明。外部世界有新变化，频道能及时接住；模型为什么慢、慢在哪一段，也终于有了能看见的依据。对于一个本地优先的多 Agent 工作台来说，这种“既能接消息，也能看过程”的感觉，价值很实在。
