## Scope and provenance

L0 is a conceptual vocabulary for describing how collaboration state changes across Actors. It helps Humans and Agents create, explain, compare, and review Multi-Actor systems. It is not an executable workflow language and does not require a complete process with a start and an end.

L0 imports the [Actor foundation](actor.md), which defines who may participate. It stays independent of business vocabulary, message transport, storage, and product implementation.

The underlying structures are not original to this project. Sequence, branching, parallel split, synchronization, partial joins, races, cancellation, loops, and termination have long histories in workflow and distributed-systems research. Cross-participant distinctions also draw from service-interaction research and contemporary Agent frameworks.

Primary antecedents include:

- [Workflow Patterns](https://research.tue.nl/en/publications/workflow-patterns-2/), van der Aalst et al., 2003.
- [Workflow Control-Flow Patterns](https://www.workflowpatterns.com/patterns/control/), Workflow Patterns Initiative.
- [Service Interaction Patterns](https://kodu.ut.ee/~dumas/ServiceInteractionPatterns/documentation.html), Barros, Dumas, and ter Hofstede, 2005.

## Core model

L0 uses three concepts: Collaboration State, Gate, and Circuit.

### Collaboration State

Collaboration State is the set of facts that later collaboration logic may need to observe: which path is active, which Actor owns work, which boundary is pending, which signals have arrived, which results remain available, or which scope has terminated.

L0 identifies the meaning of those facts, not where they live. A runtime may keep them in a call stack, memory, a database, a filesystem, a message system, an artifact graph, or another medium.

### Gate

A Gate is a business-independent class of collaboration-state transition:

```text
C ── g(event or condition) ──→ C'
```

One Gate occurrence means one committed transition. A long-running interaction is therefore represented by several Gates connected through State Elements: Call opens a Boundary State and Return or another declared outcome resolves it; Wait creates Wait State and Resume or another declared outcome resolves it. Delivery, negotiation, acceptance, and correlation may determine whether a Gate is allowed to commit, but those protocol steps are not hidden inside the Gate.

Use four terms consistently:

- **event or signal** — an observed fact that may enable a Gate;
- **Gate outcome** — the structural effect of a Gate, such as selected paths, created branches, or a committed owner;
- **completion signal** — evidence that a declared work scope reached an outcome relevant to later logic;
- **work result** — a value, artifact, or reference produced by work and potentially consumed later.

A completion signal may exist without a reusable work result. A work result may remain available after the path that produced it has completed.

### Circuit

A Circuit connects Actors, Gates, State Elements, terminal states, and typed relations. It may describe a complete collaboration or only the fragment relevant to a design question.

An arrow does not carry universal meaning. Depending on its type, it may represent enablement, a work result becoming available, a responsibility change, or a lifecycle outcome. The shorthand `X → Y` means Sequence only when completion of `X` is the declared condition that enables `Y`.

Topology alone is therefore insufficient. A useful Circuit keeps path selection, branch creation, result use, responsibility, waiting, convergence, and termination distinguishable wherever they affect the system being described.

## State Elements

A State Element is a named collaboration fact that one transition leaves available for a later transition to observe.

| State Element | What it remembers |
| --- | --- |
| **Continuation State** | Where a path may continue after the current boundary resolves |
| **Ownership State** | Which Actor owns execution or continuation |
| **Boundary State** | Which request/response or declared outcome relationship remains unresolved and where its outcome belongs |
| **Result State** | Which work result remains available and what its declared disposition is |
| **Join State** | Which inputs belong to one convergence, which have been satisfied, and whether its continuation has fired |
| **Wait State** | Which continuation is waiting and which outcomes may resolve the wait |
| **Round State** | Which loop, review, or retry round is being discussed |
| **Deadline State** | Which temporal boundary may produce a Timeout outcome |

State Elements are conceptual memory, analogous to registers or latches in the circuit metaphor. L0 does not choose their storage technology or durability guarantee.

Boundary State, Wait State, and Join State all describe unfinished collaboration relationships. They may have several possible outcomes, but one logical continuation must not be advanced twice by conflicting outcomes. After one outcome resolves or fires that continuation, a later conflicting signal is late with respect to it. L1 defines how a concrete system identifies, correlates, and commits those outcomes reliably.

Join State may refer to Result States needed downstream, but it does not merge or consume their business content.

## Four views of collaboration state

These views overlap. They are analysis lenses, not four disjoint kinds of Gate.

### Flow

Flow describes which paths exist, which are active, and which continuations may become enabled.

A lowercase **branch** is an independently advancing path. The capitalized **Branch Gate** selects candidate continuations; the Fan-out Gate creates several active branches. Keeping selection and multiplicity separate removes an important ambiguity:

```text
Branch selects one path       → no Fan-out
Branch selects several paths  → Fan-out activates them as independent branches
```

### Result Flow

Result Flow describes where a work result goes after it is produced: direct use, retention for a later consumer, joint downstream use, or terminal disposition.

Control Flow and Result Flow are related but not identical. A path may complete while its result remains available. Conversely, a convergence may observe completion signals from paths that produce no reusable result.

L0 records structural producers, retained results, and consumers. It does not define result schemas, serialization, transport, or aggregation algorithms.

### Responsibility

Responsibility describes how Actors relate to a path. At minimum, distinguish:

- **execution owner** — performs the current bounded work;
- **continuation owner** — holds the right and obligation to advance the next transition.

Visibility must not be inferred from either form of ownership; observation depends on L1 permissions and higher-level policy.

### Lifecycle

Lifecycle distinguishes active, waiting, and terminal collaboration paths or scopes. It is separate from the internal lifecycle of an Actor.

Silence is not a lifecycle outcome. Lack of activity does not prove waiting, success, failure, or termination.

## What belongs in L0

Treat an operation as an L0 Gate when it is:

1. **Business-independent** — its meaning survives a change of domain vocabulary.
2. **Semantically stable** — it produces a recognizable change in Flow, Result Flow, Responsibility, or Lifecycle.
3. **Composable** — it can participate in more than one system structure.
4. **Observable at the boundary** — its enabling fact and committed outcome can be distinguished conceptually.

L0 is a practical engineering vocabulary, not a mathematically minimal instruction set. Decomposable policies and multi-Gate structures may retain useful names, but they must be identified as configured or derived forms rather than presented as base Gates.

## Base Gates

“Base” means first-class in this vocabulary, not irreducible in a formal calculus.

### Flow Gates

#### Sequence

Enable a successor after its declared predecessor reaches the required completion outcome.

```text
Understand request → Change code → Run tests
```

Dispatching the predecessor is not completion. Sequence defines ordering, not which Actor executes either step or how information is transported.

#### Branch

Select a set of candidate continuations from an observable decision fact.

```text
Tests passed?
  ├─ Yes → Release
  └─ No  → Revise
```

The decision may come from a rule, Human, Agent, or External System. Branch defines selection, not how the decision is computed. If it selects several continuations that must advance independently, Fan-out performs the path expansion.

#### Fan-out

Expand one active path into several independently advancing branches.

```text
Research question
  ├─ Find evidence
  ├─ Find cases
  └─ Find counterexamples
```

Branches may partition work, replicate the same work, or deliberately diversify models, tools, roles, or strategies. Independent progress does not require simultaneous execution.

Fan-out does not imply a later Fan-in. Each branch may continue independently, hand off a result, wait, converge elsewhere, be cancelled, or terminate.

#### Fan-in

Observe satisfaction signals from a declared input set and enable one continuation when its convergence condition becomes satisfied.

```text
Signal A ─┐
Signal B ─┼→ Fan-in updates Join State ── ready and unfired ─→ Enable Review
Signal C ─┘

Result A ─┐
Result B ─┼→ Result State ────────────────────────────────→ Review reads results
Result C ─┘
```

Each qualifying signal is processed against Join State. It may record progress without enabling the continuation. Only the first transition from unsatisfied to satisfied for that convergence may fire the continuation; the same logical input does not satisfy the condition twice.

Fan-in defines **when and from which inputs** the Circuit continues. Aggregation, reduction, voting, selection, and synthesis define **how work results are processed**. Fan-in neither requires a preceding Fan-out nor consumes the retained work results.

A useful Fan-in description makes the relevant input set, convergence condition, membership changes, late signals, remaining branches, and reset behavior understandable when they matter.

### Responsibility Gates

#### Route

Select an Actor as the candidate for a later responsibility-bearing transition.

```text
Incoming issue → Route → Technical Actor → Delegate bounded diagnosis
```

Route chooses an Actor. It does not deliver work, prove acceptance, or change execution or continuation ownership by itself.

#### Call

Open a bounded request/response relationship with another Actor while the caller retains its continuation.

```text
Lead ── Call ──→ Search Actor
Lead continuation ←── Return(Evidence) ── Search Actor
```

The committed Call creates Boundary State around the called operation. The callee performs that operation, but Call does not reassign ownership of a pre-existing work scope. Any delivery or acceptance needed before the boundary is established belongs to L1.

The boundary may later resolve through Return or another declared outcome such as Timeout or an observed Stop status that the Circuit defines as boundary-resolving. A Cancel request alone is not that outcome. Once resolved, a late outcome cannot advance the same continuation again.

#### Delegate

Assign execution ownership of an explicitly bounded work scope to another Actor.

```text
Lead ── Delegate "own the test plan" ──→ QA Actor
```

The delegator may wait for an outcome or continue independently. When an outcome is expected, the Circuit may combine Delegate with a Call/Return-style Boundary State; the responsibility change and the request/response shape remain distinct. Delegate does not decide final accountability, redelegation, permissions, or budget propagation. Any required acceptance precedes the committed L0 ownership change.

#### Transfer

Commit continuation ownership for a path to another Actor.

```text
Frontline Support ── Transfer ──→ Specialist → Resolution
```

Transfer is not a proposal, delivery, or acceptance event. Those may authorize the commit at L1. After Transfer commits, the previous Actor is no longer required for the path to advance.

#### Return

Resolve a Call Boundary State, or an outcome boundary explicitly composed with Delegate, using a completion signal and, when applicable, a work result.

```text
Worker → Return(completed | partial | failed | rejected | blocked | cancelled)
       → declared continuation
```

Return is the Actor-produced boundary outcome; silence is not Return. Timeout or an observed Stop status that the Circuit declares boundary-resolving may resolve the Boundary through alternative paths rather than fabricated Returns.

An outcome such as `blocked` resolves the Boundary only when the Circuit declares it terminal for that relationship; otherwise the Boundary remains pending.

### Lifecycle Gates

#### Wait

Move an active path into a Wait State that preserves its continuation and names its possible resolution outcomes.

```text
Submit change → Wait for approval
```

Waiting is neither failure nor termination.

#### Resume

Resolve a Wait State through its declared success signal and restore the preserved continuation.

```text
Approval arrives → Resume → Deploy
```

Timeout or an observed `Stop(cancelled)` may resolve the same Wait through alternative outcomes. A Cancel request alone does not. Once one outcome resolves the Wait, later conflicting signals do not reopen it.

#### Stop

End a declared collaboration path or scope with an explicit terminal status, such as succeeded, failed, cancelled, rejected, or not satisfied.

```text
Review passed       → Stop(succeeded)
Round limit reached → Stop(not_satisfied)
```

Stop affects only its declared scope. Whether related branches, child scopes, or pending boundaries are cancelled, detached, or allowed to continue is a property of the surrounding Circuit or L2 system.

## Configured and derived forms

These names are useful at L0 but are not peers of the base Gates.

### Fan-in policies

#### Race

Continue from the first eligible input that satisfies an acceptance condition. Race must make the winner rule and the fate of non-winning or near-simultaneous inputs understandable.

#### Quorum

Continue after a declared number or weight of eligible inputs satisfies a condition. One logical input contributes at most once. Quorum must expose membership, threshold, and remaining-input behavior.

`All`, `First acceptable`, and `Quorum` are convergence policies. A deadline may close the observation window through a Timeout path, but choosing the best available work result remains a downstream selection operation.

### Non-synchronizing convergence

#### Simple Merge

Let mutually exclusive or otherwise non-concurrent paths share one successor without waiting for one another.

```text
Branch
  ├─ Path A ─┐
  └─ Path B ─┴→ Next
```

Simple Merge has no Join State. If several incoming paths may be active and each arrival should activate the successor, that is repeated activation, not synchronization.

### Alternative resolution

#### Timeout

Produce a timeout outcome when a declared deadline is crossed for a pending relationship or operation.

```text
Wait for approval
  ├─ Approval arrives → Resume → Deploy
  └─ Deadline passes  → Timeout → Escalate
```

Timeout resolves the waiting or controlling relationship, but it does not necessarily stop the underlying Actor work. The surrounding Circuit must decide the fate of that work and of any late result.

### Directed termination request

#### Cancel

Request that a declared target path or scope terminate as cancelled.

```text
Winner selected → Cancel(non-winning branches) → cancellation requested
Non-winning branch → Stop(cancelled)
```

Cancel and Stop are different facts. Cancel produces a directed request; committed termination is observed as Stop. If another continuation must wait for termination, the Circuit must say so rather than treating the request itself as completion.

### Repetition

#### Loop

Create a back edge to an earlier Circuit region until a declared termination condition holds. A Loop must expose a round limit and may also expose a time limit.

#### Retry

Repeat a declared operation after selected outcomes and within an attempt limit. Retry is a failure-conditioned Loop with additional concerns about delay, earlier effects, and late outcomes.

## Distinctions that must remain visible

| Do not conflate | Distinction |
| --- | --- |
| Branch / Fan-out | Branch selects continuations; Fan-out creates independently advancing branches. |
| Fan-out / Broadcast | Fan-out creates work paths; Broadcast changes information visibility. |
| Fan-out / Fan-in | Fan-out creates branches; Fan-in observes convergence. Neither requires the other. |
| Fan-in / Reduce | Fan-in controls when to continue; Reduce processes content. |
| Simple Merge / Fan-in | Simple Merge shares a successor without waiting; Fan-in waits for a convergence condition. |
| Flow / Result Flow | Flow identifies enabled paths; Result Flow identifies the fate of work results. |
| Branch / Route | Branch selects continuations; Route selects an Actor. |
| Route / Transfer | Route selects a candidate; Transfer changes continuation ownership. |
| Call / Delegate | Call creates a request/response boundary; Delegate reassigns execution ownership of an explicit work scope. They may be composed. |
| Delegate / Transfer | Delegate changes the executor of a scope; Transfer changes the continuation owner of a path. |
| Wait / Stop | Wait preserves a continuation; Stop creates a terminal outcome. |
| Cancel / Stop | Cancel requests another scope to terminate; Stop is committed termination. |
| Race / Voting | Race selects the first qualifying input; Voting is one possible result-processing mechanism. |
| Gate / Circuit | A Gate is one transition class; a Circuit connects transitions and remembered facts. |
| Circuit / Pattern | A Circuit describes collaboration structure; a pattern resolves recurring forces and includes consequences. |

## Using L0 to create or analyze a system

L0 is useful when it makes consequential design choices visible. For the Circuit fragment under discussion, ask only the questions that apply:

- Which participants are Actors at this boundary?
- Which Gate changes each path, responsibility, wait, or terminal outcome?
- When several paths are selected, where does Fan-out create independent branches?
- Where does each relevant work result go?
- Who owns execution, and who owns continuation?
- Which State Elements preserve facts needed later?
- Which outcomes may resolve each Wait or Boundary, and can a conflicting late outcome advance it again?
- What inputs and policy make each Fan-in ready, and what happens to the remaining branches?
- What bounds each Loop or Retry?
- What exact scope does Stop terminate?

An L0 analysis may intentionally leave implementation questions open. Its job is to expose the collaboration meaning and any semantic ambiguity, not to invent missing protocol details.

## What L0 does not define

L0 leaves the following concerns to other layers:

- concrete Actor identifiers, discovery, or addresses;
- message and artifact formats;
- delivery, acknowledgement, ordering, duplication, or idempotency mechanisms;
- correlation and causation representation;
- durable storage, offline behavior, recovery, or resumption transport;
- permissions, trust, budgets, or delegation policy;
- result aggregation algorithms;
- complete Multi-Actor system compositions;
- collaboration design patterns and their consequences.

L1 represents concrete Gates, state, correlation, timing, and communication choices. Runtime and the Durable Execution Plane implement persistence and recovery. L2 composes those parts into complete Multi-Actor systems.
