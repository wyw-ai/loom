# L1: Actor Circuit YAML

## Status

L1 is an experimental `v0alpha1` YAML representation of the L0 vocabulary. It is designed to remain readable before a CLI exists.

L1 is not a universal execution language. It records enough meaning for a Human, Agent, or future CLI to explain, compare, evaluate, visualize, and bind an Actor Circuit to a product.

L1 assets inform a design; they do not generate it. A Gate YAML says what structure exists and what may be configured. A channel YAML says what a communication medium will do to that structure and which pitfalls to design around. A Circuit YAML records how one design reasoned about those choices — it is a reference for comparison, not a workflow template to instantiate.

## Design principle

Agent systems need both fixed configuration and open judgement:

> Put stable choices in parameters. Put context-dependent judgement in prompts. Keep runtime facts in state. Keep evaluation claims in evidence.

This separation protects evaluation integrity:

- a parameter is resolved before execution and cannot be rewritten after the outcome;
- a prompt may express fuzzy criteria without pretending they form a universal enum;
- state records what is currently true while the Circuit runs;
- evidence records enough of the run to explain and compare the result.

The exact prompt used by an evaluation is still frozen and recorded. Freezing one run does not turn its open semantics into a global enum.

## Relationship to L0

```text
L0  Human-readable definitions
    What Sequence, Fan-out, Transfer, Wait, and other Gates mean

L1  YAML definitions and Circuit descriptions
    Which Gates are used, which parameters are fixed, where judgement remains open,
    what must be remembered, and how cross-Actor communication behaves
```

Communication is one part of L1. L1 also describes the collaboration process, state, and evaluation surface.

## Asset layout

```text
assets/l1/
├── gates/       One readable YAML file for every L0 base Gate
├── configured/  Race, Quorum, Simple Merge, Timeout, Cancel, Loop, and Retry
├── circuits/    Complete processes built from Gates
├── channels/    How a communication medium behaves and what to watch for
└── bindings/    How products represent a Circuit
```

## Gate YAML

A Gate file defines one operation and the choices a Circuit may configure. It does not select those choices for a particular run.

```yaml
version: v0alpha1
kind: gate
name: fan-in

description: Observe satisfaction signals from declared inputs and enable one continuation when the convergence rule is satisfied.

input:
  declared_inputs: many
  satisfaction_signal: one_at_a_time

output:
  continuation: enabled_once

parameters:
  completion_rule:
    type: enum
    values: [all, first_acceptable, quorum]
    required: true

  quorum:
    type: integer
    minimum: 1
    required_when:
      completion_rule: quorum

  qualification_method:
    type: enum
    values: [any_signal, rule, prompt, human, external]
    required_when:
      completion_rule: [first_acceptable, quorum]

  late_signals:
    type: enum
    values: [ignore, record_without_reopening]
    required: true

  corrections:
    type: enum
    values: [first_counts, latest_supersedes]
    required_when:
      qualification_method: [prompt, human]

  remaining_inputs:
    type: enum
    values: [request_cancel, ignore, keep_running]
    required_when:
      completion_rule: [first_acceptable, quorum]

  after_request_cancel:
    type: enum
    values: [continue_without_waiting, wait_for_stop]
    required_when:
      remaining_inputs: request_cancel

prompt_slots:
  qualifying_signal:
    required_when:
      qualification_method: prompt
    purpose: Describe what makes an input signal count toward continuation.

state:
  remembers: [join_id, expected_inputs, satisfied_inputs, convergence_satisfied, continuation_fired]

evidence:
  records: [resolved_parameters, satisfaction_signals, join_state_updates, continuation_decision]

rules:
  - Fan-in changes Join State; work results remain in separate Result State.
  - One logical input may satisfy the convergence condition at most once.
  - With latest_supersedes, a correction replaces the input's earlier satisfied signal; the superseded signal never counts toward convergence.
```

The common fields answer different questions:

| Field | Question answered |
| --- | --- |
| `description` | What does this Gate do? |
| `input` / `output` | What enters and leaves it? |
| `parameters` | Which values must or may be fixed before execution? |
| `prompt_slots` | Which decisions remain open and need contextual instructions? |
| `state.remembers` | Which runtime facts must remain observable? |
| `evidence.records` | Which facts must be retained to explain or evaluate the result? |
| `rules` | Which semantic distinctions must never be weakened? |

Only include a section when the Gate actually needs it. Sequence has no fuzzy judgement. A prompt-driven Route does.

## Parameters and prompts

Use a parameter when changing the value creates a meaningfully different, comparable run:

```yaml
parameters:
  completion_rule:
    type: enum
    values: [all, first_acceptable, quorum]

  max_attempts:
    type: integer
    minimum: 1

  timeout:
    type: duration
```

Typical parameters include:

- completion, retry, timeout, and terminal policies;
- synchronous or asynchronous interaction;
- immediate or store-and-forward delivery;
- thresholds, limits, correlation keys, and late-result policies;
- deterministic selection and tie-breaking methods.

Use a prompt slot when no small stable value set captures the decision honestly:

```yaml
prompt_slots:
  acceptance_criteria:
    required_when:
      acceptance_method: prompt
    purpose: Describe what makes a candidate good enough to continue.
```

Typical prompt semantics include:

- whether a result is good enough for the current task;
- how quality, risk, novelty, or usefulness should be judged;
- how an ambiguous request should be routed;
- when another reasoning or revision round is worthwhile.

Do not create an enum merely because a CLI can validate it. A false enum makes an evaluation repeatable but less representative of the real task.

## Circuit YAML

A Circuit records a finished design. Write one when a complete process must be frozen for evaluation, compared with another run, handed off, or bound to a product; it is the end of design work, not its starting point. The bundled files are instances of complete reasoning, not templates to start from.

A Circuit selects Gate parameters with `with`, supplies prompts when needed, connects observable outcomes, and chooses where state lives:

```yaml
version: v0alpha1
kind: circuit
name: first-acceptable-research

prompts:
  acceptable_evidence: |
    Count a completion signal only when its referenced result is supported by
    primary sources and directly answers the research question.

memory:
  research_join: {store: durable}
  research_results: {store: durable, consumer: synthesize}

steps:
  converge:
    gate: fan-in
    input:
      declared_inputs: research_inputs
      satisfaction_signal: research_completion_signal
    with:
      completion_rule: first_acceptable
      qualification_method: prompt
      remaining_inputs: request_cancel
      after_request_cancel: continue_without_waiting
      late_signals: record_without_reopening
      corrections: latest_supersedes
      mode: asynchronous
      delivery: store_and_forward
      activation: wakes
      match_by: [work_id, input_id]
    prompt:
      qualifying_signal: acceptable_evidence
    then:
      enabled_once: synthesize
```

The Circuit vocabulary is:

| Field | Question answered |
| --- | --- |
| `instance_of` | Which recognized L2 structure does this Circuit instantiate? |
| `uses` | Which L0 Gates or configured forms appear? |
| `actors` | Who participates? |
| `parameters` | Which Circuit-wide values are fixed? |
| `prompts` | Which open instructions are supplied or referenced? |
| `memory` | What must be remembered and where does its truth live? |
| `start` | Which step begins the Circuit? |
| `steps` | Which base Gate or configured L0 form drives each step? |
| `input` | How this step binds the Gate's declared inputs? |
| `with` | Which Gate parameter values are selected at this step? |
| `prompt` | Which prompt fills a Gate prompt slot or accompanies a request? |
| `then` | Where does each observable outcome continue? |
| `evaluation` | What must be frozen and recorded for comparison? |
| `rules` | Which Circuit-wide guarantees matter? |

## Evaluation

A comparable evaluation run freezes the resolved configuration before execution and records the resulting trace:

```yaml
evaluation:
  freeze:
    - resolved_parameters
    - resolved_prompts
    - actor_bindings
  record:
    - inputs
    - state_transitions
    - messages
    - decisions
    - outputs
```

For an evaluation to be meaningful:

1. resolve every required parameter before the run;
2. preserve the exact prompt text or immutable prompt reference;
3. preserve the Actor and model or service bindings outside or through the ProductBinding;
4. record decisions, not only final answers;
5. reject missing required evidence rather than inferring success from silence.

Parameters make runs comparable. Prompts keep the task realistic. Evidence makes the comparison auditable.

## Memory

Every remembered fact chooses one storage meaning:

```yaml
memory:
  pending_call: {store: ephemeral}
  continuation_owner: {store: durable}
  current_draft: {store: external}
```

| Store | Meaning |
| --- | --- |
| `ephemeral` | Needed only while the current live execution exists |
| `durable` | Must survive the Circuit's declared time or failure boundary |
| `external` | Another product is the source of truth; the Circuit keeps a reference |

These are retention requirements, not database choices.

### Derived state

Local caches, ledgers, and scratch files are derived state, not a fourth store. They must be rebuildable from durable or external collaboration facts. Publish the visible collaboration action before or together with the local transition, and never let derived state override newer collaboration facts.

## Communication

Cross-Actor Gates expose stable communication choices as parameters:

```yaml
with:
  mode: asynchronous
  delivery: store_and_forward
  activation: wakes
  visibility: shared
  match_by: [work_id, transfer_id]
```

### `mode`

- `synchronous` — the current continuation waits for the interaction;
- `asynchronous` — the result may arrive later and must match pending work.

### `delivery`

- `immediate` — assumes a live interaction and creates no stored delivery obligation;
- `store_and_forward` — delivery may remain pending until consumed or expired.

Interaction timing and state retention remain independent. A synchronous interaction may write durable state; an asynchronous interaction may carry only an external reference.

### `activation`

- `wakes` — delivery triggers the recipient's next turn: the message carries a continuation the recipient must advance;
- `notify_only` — delivery is recorded without triggering a turn: status, receipts, background context.

A message that requests action must wake. Natural-language urgency — "everyone please start" — does not create a wake, and a continuation is never advanced by a message that did not activate its owner.

When a message wakes an Actor, that turn ends only with the continuation's ownership explicit: an answer delivered, a next Actor woken, state committed, a wait or recheck scheduled, or an explicit no-action. Never let a turn end with the continuation unaccounted for.

### `visibility`

- `shared` — visible to every participant in the scope;
- `restricted` — visible to named recipients only.

A reply to a restricted message stays within the same audience. Prefer restricting in scope over opening a separate private channel, so the reply remains attached to the workflow context. Naming an Actor as the subject of a message is not the same as adding it to the audience — and on chat media, an `@` mention usually wakes. A shared message must not leak restricted state; even a one-word answer can.

### `match_by`

Correlation identities attach a later event to the correct work, call, branch, transfer, wait, attempt, or round.

Delivery cannot stand in for acceptance, and acceptance cannot stand in for ownership commitment.

## Channels

Communication parameters (`mode`, `delivery`, `acknowledgement`, `match_by`) are medium-independent vocabulary. A channel asset describes one medium in that vocabulary: what an agent should expect, which choices the medium forces, and which pitfalls to design around.

A channel asset answers different questions per field:

| Field | Question answered |
| --- | --- |
| `traits` | What is inherently true of this medium? |
| `capabilities` | Which abilities vary by product, and which L1 choices does each one affect? |
| `caveats` | What goes wrong in practice, why, and how is it handled? |

Each caveat is written for an agent in the middle of a design: `observe` names the symptom it will see, `because` explains the mechanism, `handle` gives the design response, and `affects` links back to Gates, parameters, or L1 concerns.

A channel asset never names a concrete product. A pitfall that survives switching products belongs here; a fact only one product has belongs in that product's ProductBinding. The `capabilities` list is the bridge: it defines the questions a ProductBinding must answer for this medium.

See [../assets/l1/channels/im.yaml](../assets/l1/channels/im.yaml) for instant messaging.

## Configured forms

Race, Quorum, Simple Merge, Timeout, Cancel, Loop, and Retry each have YAML while retaining their L0 identity:

- Race and Quorum are Fan-in policies;
- Simple Merge is a non-synchronizing Circuit form;
- Timeout is a resolution outcome;
- Cancel is a directed termination request;
- Loop and Retry are Circuit forms.

Their stable policies and limits are parameters. Their task-dependent quality judgements remain prompt slots.

## Product bindings

A ProductBinding explains how one real product supplies the Circuit's Actors, parameters, prompts, memory, steps, communication, and evidence:

```yaml
version: v0alpha1
kind: product-binding
name: example-product-and-circuit

circuit: accepted-transfer

product:
  name: example-product

map:
  actors: {}
  parameters: {}
  prompts: {}
  memory: {}
  steps: {}
  communication: {}
  evidence: {}

missing: []
```

Use `missing` when the product cannot represent a required fact directly. Do not silently weaken a Circuit to fit a product.

## Boundary with runtime and L2

```text
L0       Defines the concepts in prose.
L1       Represents Gates and Circuits as readable YAML.
Runtime  Provides processes, storage, delivery, timers, and recovery.
L2       Builds complete Multi-Actor systems from these pieces.
```

A future CLI may resolve and validate parameters, freeze evaluation manifests, draw diagrams, compare traces, and generate ProductBinding skeletons. The YAML remains useful without that CLI.
