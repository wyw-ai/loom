# L2: Multi-Actor Systems

## Status

L2 is a preview. The taxonomy below is a working draft, and every entry describes a structure observed in real systems rather than an invented one. Neither is an established industry standard.

## What makes a system L2

L2 answers **how Actors, L0 circuits, and L1 communication form a complete Multi-Actor system**.

A description earns the name of an L2 structure only when it answers all seven questions:

1. **Actor boundaries** — who participates, and where each boundary lies;
2. **State ownership** — which State Elements exist, and who holds each one;
3. **Circuit** — which L0 Gates connect them, in what shape;
4. **Protocol assumptions** — which L1 communication choices the shape depends on;
5. **Convergence rules** — how the system knows its parts have come together;
6. **Failure behavior** — what happens when any participant stops answering;
7. **Termination conditions** — what ends, who declares it, and over what scope.

A name alone is not a description. Fan-out followed by Fan-in is an L0 circuit, not an L2 system: it answers question 3 and none of the others. Conversely, a real L2 system may compose several structures; each entry below describes one position in the design space, not a mutually exclusive category.

One guardrail against pattern-catalog invention: a structure enters this file only after it has been observed in at least one real system. This file reorganizes engineering experience; it does not invent new structures.

## The two axes

**Axis 1 — Continuation topology: where does the primary continuation live?**

| Value | Meaning |
| --- | --- |
| `single-holder` | One Actor holds the main continuation and the Join State |
| `passing` | The continuation moves along a Transfer chain or delegation tree |
| `contended` | Any participant may initiate the next step; allocating the continuation is itself the collaboration problem |
| `implicit` | No explicit continuation; shared state changes drive the next action |

**Axis 2 — Decision locus: what fills the runtime judgement points?**

| Value | Meaning |
| --- | --- |
| `rule` | Fixed at design time; every path exists in the circuit before the run |
| `prompt` | An LLM judges at runtime; the path comes into existence during the run |
| `human` | A person decides: approvals, arbitration, escalation |
| `market` | No single decider; the outcome emerges from distributed bids or votes |

The two axes are independent. The same circuit shape with a different decision locus is a different system: a rule-driven Orchestrator–Worker is replayable and statically verifiable, while a prompt-driven one chooses its path during the run and must freeze prompts to stay evaluable.

## Entries

### Orchestrator–Worker

`continuation: single-holder` · `decisions: rule or prompt`

**Context and forces.** A task decomposes into independent subtasks that different Actors can perform, and someone must see the whole picture. The tension: centralized visibility and control against worker autonomy; a single convergence point against a single point of failure.

**Actor boundaries.** One orchestrator and any number of workers. The orchestrator decomposes, dispatches, and converges; it does not perform the work. Workers see only their own bounded scope and have no global view.

**State ownership.** The orchestrator holds the main continuation, branch_membership, Join State, and result references. Each worker holds only its own execution state. Everything the orchestrator needs in order to survive a restart requires `store: durable`.

**Circuit.** Fan-out creates branches; Delegate commits each branch's execution owner; Call and Return open and resolve each branch boundary; Fan-in converges completion signals; Branch assesses acceptable outcomes; Stop ends the declared scope.

```text
              ┌─ branch 1: delegate → call/return ─┐
fan-out ──────┼─ branch 2: delegate → call/return ──┼── fan-in ── branch (assess) ── stop
              └─ branch 3: delegate → call/return ─┘
```

See [all-branches-fan-out-fan-in](../assets/l1/circuits/all-branches-fan-out-fan-in.yaml) for a recorded instance.

**Protocol assumptions.** Branches cross Actor boundaries: delivery is `store_and_forward`, correlation carries `[work_id, fanout_id, branch_id]`, and Delegate requires acceptance before commit. Over instant messaging, every caveat in [im.yaml](../assets/l1/channels/im.yaml) applies — branch identities must live in the messages, not in the platform.

**Convergence rules.** Fan-in observes completion signals under a declared `completion_rule` (`all`, `quorum`, or `first_acceptable`). A separate Branch reads the retained outcomes to decide success; Fan-in itself never reads result content.

**Failure behavior.** A silent worker leaves its boundary unresolved until the declared timeout outcome fires. A failed branch counts as returned but is not acceptable. The orchestrator is the single point of failure: without durable Join State, its death loses the whole circuit.

**Termination conditions.** When the convergence rule is satisfied, the assessment Branch selects succeeded or not_satisfied, and Stop terminates `circuit_scope` — never a larger implicit scope. The orchestrator may cancel remaining branches; over an unreliable medium, cancel is a request, not a guarantee.

**Consequences.** Simple to reason about, easy to observe, easy to bind to products. The costs: the orchestrator is a bottleneck and a single point of failure, workers cannot adapt to what they cannot see, and the prompt-driven variant must freeze prompts to stay evaluable. The rule-driven variant is essentially a workflow with explicit acceptance semantics.

### Recursive Delegation

`continuation: passing (tree)` · `decisions: usually prompt`

**Context and forces.** The decomposition depth is unknown at design time: any node may discover that its assigned scope needs further splitting. The tension: local autonomy against global control — no node sees the whole tree, yet someone must bound depth, budget, and termination.

**Actor boundaries.** A tree. Every internal node is both delegatee (toward its parent) and delegator (toward its children). Each delegation is its own bounded Actor relationship; sibling subtrees know nothing of each other.

**State ownership.** No node holds global state. Each node holds only its own layer: its pending boundary toward its parent, its child branches and Join State, and its budget remainder. Depth and budget travel downward as explicit delegation context — they are parameters of the delegation, not ambient knowledge.

**Circuit.** Each node locally runs a small orchestrator shape — Delegate, Call/Return per child, Fan-in — and its own Return resolves its parent's boundary. Results flow back up layer by layer; each layer may aggregate, but aggregation semantics are declared per layer, not assumed.

```text
root ── delegate ── node ──┬─ delegate ── leaf ── return ──┐
                           ├─ delegate ── node ── ... ─────┼── node fan-in ── return ── root fan-in
                           └─ delegate ── leaf ── return ──┘
```

**Protocol assumptions.** Correlation needs path identity: `work_id` plus each layer's delegation identity, or a late signal cannot be attributed to its subtree. Cancel propagation down the tree is a protocol obligation, not something the medium provides. Over chat media, `human-correlation-is-fragile` applies at every layer.

**Convergence rules.** Each layer converges independently under its own `completion_rule`. A parent's satisfaction signal is its children's Returns. A subtree that cannot converge reports a non-acceptable outcome upward instead of hanging.

**Failure behavior.** The hardest case is a middle node dying: its subtree becomes orphaned work that may keep consuming budget. Leases or timeouts at the parent layer are the only containment. A leaf failure is absorbed or reported by its parent's declared policy — per layer, explicitly.

**Termination conditions.** Depth limits and budget limits travel with every delegation and are enforced at each layer. Cancel names a subtree scope; Stop at any node terminates only its own subtree. The root ends the whole tree only by cascading declared scopes, not by magic.

**Consequences.** The most expressive structure in this file and the hardest to operate. Global progress is invisible by construction, prompt-driven decomposition can run away, and evaluation is the hardest of any entry here — freeze every layer's prompts and budgets or comparisons are meaningless. Use when the problem's shape is genuinely unknown; reach for Orchestrator–Worker when the decomposition is knowable in advance.

### Group Chat

`continuation: contended` · `decisions: rule, prompt, or free`

**Context and forces.** The problem benefits from emergent multi-perspective discussion and does not decompose cleanly in advance. The tension: openness against convergence — an open floor surfaces more, and it also never ends on its own.

**Actor boundaries.** Participants are peers. An optional moderator holds the floor-allocation decision but carries no content authority by default. The shared message stream is a channel, not an Actor.

**State ownership.** The transcript is a shared fact — `durable`, `external`, or both. Each participant holds a private view of context. Crucially, no participant naturally holds "whether the discussion is sufficient"; that judgement must be explicitly assigned, or the system cannot converge.

**Circuit.** There is no fixed step graph. Each turn is: select the next speaker (Route or Branch over participants), Call, Return, append to transcript. The one non-negotiable Gate is a declared convergence check.

```text
repeat:
  pick next speaker ── call ── return ── append transcript ── convergence check
                                                                    │
                                            sufficient ── stop  /  not yet ── repeat
```

**Protocol assumptions.** The medium is usually chat, so three caveats from [im.yaml](../assets/l1/channels/im.yaml) dominate: `broadcast-is-not-fan-out` (a message reaches everyone but creates no branches), `human-correlation-is-fragile` (references get lost), and `silence-means-nothing` (a quiet participant is not an agreeing one). Turn order is the continuation allocation and must be explicit: round-robin (rule), moderator picks (prompt), or free-for-all with a declared tie-break.

**Convergence rules.** The hardest section of this entry. Options: the moderator judges sufficiency (prompt), a fixed round budget expires (rule plus round counter), or a proposal is tabled and voted (Quorum). Pick one at design time; "we will know it when we see it" is not a convergence rule.

**Failure behavior.** A participant dropping out degrades representativeness while the discussion continues — decide whether that is acceptable. A moderator dying stalls continuation allocation entirely; a succession rule is required. A runaway discussion is itself a failure mode: budget exhaustion must be a declared outcome, not an operator intervention.

**Termination conditions.** The convergence rule fires, or the round or time budget expires. Either way, Stop names the discussion scope. Without one of these two, a Group Chat does not terminate.

**Consequences.** The most flexible and least predictable structure here. Transcripts grow without bound, token costs follow, and runs do not repeat — evaluation compares decision records, not paths. Reach for it when exploration matters more than efficiency; never as a default.

### Contract Net

`continuation: single-holder, then passing` · `decisions: market`

**Context and forces.** Who should perform a task is unknown at design time, and candidates differ in capability, load, or cost. The tension: allocation quality against negotiation overhead — every bid round is time and messages spent before work begins.

**Actor boundaries.** One initiator and any number of bidders. Bidders may decline or stay silent. After award, the winner becomes an ordinary worker with its own boundary; losers return to the pool.

**State ownership.** The initiator holds the call-for-proposals identity, the bid-collection Join State, and the award decision. Until award, no execution ownership exists anywhere. After award, the winner holds its execution boundary; the initiator retains only the result expectation.

**Circuit.** Two phases. Award: Fan-out carries the call for proposals; Fan-in collects bids under quorum or timeout; Branch evaluates bids and selects a winner; Delegate awards with required acceptance. Execution: the awarded branch then runs the ordinary Call/Return/Fan-in shape. Losing bidders receive an explicit reject so their held offers are released.

```text
fan-out (cfp) ── fan-in (bids: quorum or timeout) ── branch (evaluate) ── delegate (award)
                                                                            │
                            losers: explicit reject ◄───────────────────────┴── winner: call/return ── fan-in ── stop
```

**Protocol assumptions.** A bid is a satisfaction signal carrying a payload: price, ETA, confidence. Correlation carries `[cfp_id, bid_id]`. Timeout on bid collection is mandatory — waiting for every bidder means never awarding. Award requires acceptance before commit: an unanswered award is not a contract.

**Convergence rules.** Two distinct convergences; do not merge them. Bid collection converges under `quorum` or timeout. The awarded work converges under its own `completion_rule`, exactly as in Orchestrator–Worker.

**Failure behavior.** A bidder's silence is simply no bid. The dangerous failure is the winner dying after award: its boundary times out, and recovery is a new award round under a fresh `cfp_id` — never a silent re-award inside the old one. A winner that stops performing after accepting is a real risk; evidence must record the acceptance and the progress signals.

**Termination conditions.** No acceptable bids ends as not_satisfied. After award, termination follows the single-holder shape. Cancel before award ends the round; cancel after award is a request to the winner, with the usual medium caveats.

**Consequences.** Better allocation than static routing, at the price of negotiation latency and protocol complexity. The bid-comparison criterion is a prompt slot, not an enum — "best" mixes price, trust, and context. This is the only entry whose decision locus is market: the initiator writes the evaluation rule, but the candidates that rule sees exist only because bidders chose to speak.

## Using L2

These entries are a coordinate system and a checklist, not system templates. To design a complete system: locate its position on the two axes, answer the seven questions for that position, and record the result as an L1 Circuit when it must be frozen, compared, or bound. To analyze an existing system, do the same in reverse — its coordinates and its unanswered questions usually explain its incidents.

When observing a running system, check where its interaction history contains feedback cycles. Tree-like, non-repeating histories — fan-out pipelines, one-shot calls — usually admit aggregate monitoring. Cyclic histories — tight Evaluator–Optimizer rounds, Group Chat, anything sharing a board — are exactly where counts and rates mislead; analyze those through their State Elements and evidence, not through dashboards.
